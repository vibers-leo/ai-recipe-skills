# CS 패턴 (에러·실패·제한 메시지)

사용자가 가장 많이 CS 문의를 만드는 지점이 바로 **에러·실패·제한 메시지**다. 이 메시지가 차가우면 사용자는 "내가 뭘 잘못했나?" → "도움을 받아야겠다" → CS 문의로 이어진다. 반대로 잘 설계된 메시지는 사용자가 스스로 해결하게 만든다.

## 토스 에러 메시지 시스템의 3요소

토스는 에러 메시지를 아래 3가지 요소로 구성한다:

1. **무슨 일이 일어났는지 (What)** — 사용자 관점에서 간결하게
2. **왜 일어났는지 (Why)** — 필요한 경우에만, 사용자가 알아야 할 이유만
3. **어떻게 해결하는지 (How)** — 가능한 가장 구체적인 해결 경로

가장 중요한 건 **How**다. 해결 경로가 없는 에러 메시지는 "죄송합니다"를 1000번 써도 CS 문의를 막지 못한다.

## 에러 유형별 템플릿

### A. 일시적 시스템 오류 (네트워크, 서버)

원본: "오류가 발생했습니다. 잠시 후 다시 시도해주세요."

개선:
```
문제가 생겼어요.
잠시 후 다시 시도해볼게요.
```

또는 원인을 알고 있다면:
```
네트워크가 불안정해요.
연결을 확인하고 다시 시도해볼게요.
```

**핵심:** "오류"라는 차가운 단어를 "문제", "어려움"으로 바꾼다. 주체를 "제가/우리가"로 슬쩍 숨겨서 사용자 탓이 아니란 느낌을 준다.

### B. 입력 검증 실패 (폼 에러)

원본: "유효하지 않은 이메일입니다."

개선:
```
이메일 형식이 맞지 않아요.
예: name@domain.com
```

원본: "비밀번호는 8자 이상, 특수문자를 포함해야 합니다."

개선:
```
비밀번호는 8자 이상, 특수문자가 필요해요.
```

**핵심:** "유효하지 않다", "필수입니다" 같은 경직된 표현을 없앤다. 가능하면 **예시**를 함께 보여준다. 사용자가 스스로 고칠 수 있게.

### C. 권한·제한 에러

원본: "권한이 없습니다."

개선:
```
이 기능은 아직 사용할 수 없어요.
[프로필 인증하기] 버튼을 눌러주세요.
```

원본: "본인인증이 필요합니다."

개선:
```
본인인증을 먼저 해요.
[본인인증 시작하기]
```

**핵심:** 제한에는 **항상 다음 행동**을 제시한다. 제한만 알리고 해결 경로를 안 주면 사용자는 이탈한다.

### D. 한도·수량 초과

원본: "일일 한도를 초과하였습니다."

개선:
```
오늘 사용할 수 있는 한도를 다 썼어요.
내일 다시 시도하거나, [한도 늘리기]를 신청해볼 수 있어요.
```

**핵심:** "초과"는 사용자를 비난하는 느낌이 든다. "다 썼어요"는 중립적이다. 그리고 한도를 풀 수 있는 방법이 있다면 즉시 제시한다.

### E. 찾지 못함 (Not Found)

원본: "결과가 없습니다."

개선:
```
검색 결과가 없어요.
다른 검색어로 찾아볼까요?
```

원본: "페이지를 찾을 수 없습니다. (404)"

개선:
```
찾으시는 페이지가 없어요.
주소를 다시 확인하거나, [홈으로 가기]를 눌러보세요.
```

**핵심:** "없다"로 끝나면 막다른 길이다. 다음 행동을 반드시 제시.

### F. 결제·거래 실패

원본: "결제에 실패하였습니다."

개선:
```
결제를 완료하지 못했어요.
카드 정보를 확인하고 다시 시도해볼게요.
문제가 계속되면 [카드사로 문의하기]
```

**핵심:** 결제 실패는 사용자가 가장 불안해하는 순간이다. 원인(사용자 쪽 vs 시스템 쪽)을 가능한 한 알려주고, 최종 fallback으로 문의 경로를 제공한다.

## 절대 피해야 할 표현

다음 표현은 **CS 문의를 직접적으로 유발**한다. 보이면 즉시 제거한다.

- "관리자에게 문의하세요" → 대체: "[문의하기]" 버튼 + 문의 폼으로 바로 연결
- "잠시 후 다시 시도해주세요" (구체성 없음) → 대체: "잠시 후 다시 시도해볼게요" (시스템이 함께 있는 느낌)
- "시스템 오류 코드: ERR_500_XYZ" (사용자 노출 금지, 로그로만)
- "죄송합니다" (사과로 시작) → 대체: 바로 상황 설명부터. 사과는 정말 중대한 장애에만.
- "알 수 없는 오류" → 대체: "문제가 생겼어요" + 최소한의 맥락
- "해당 기능은 지원되지 않습니다" → 대체: "이 기능은 준비 중이에요" + 출시 예정 정보

## 사과의 품격

사과는 강력한 도구지만 남발하면 무의미해진다.

- **절대 안 함:** 일반 에러, 입력 실패, 경량 오류
- **가끔 함:** 결제 실패, 데이터 손실 가능성
- **반드시 함:** 서비스 장애, 보안 사고, 약속 불이행

사과할 때도 "죄송합니다" 대신 "불편을 드려 죄송해요" 같은 구체적인 표현이 낫다.

## 빈 상태(Empty State)도 CS 관점에서

에러는 아니지만, **아직 데이터가 없는 상태**도 사용자에게 "내가 뭘 잘못했나?" 느낌을 줄 수 있다. 빈 상태는 반드시 **다음 행동 버튼**과 함께.

```
원본: 등록된 상품이 없습니다.
개선: 아직 등록한 상품이 없어요. [첫 상품 올리기]
```

```
원본: 검색 결과가 없습니다.
개선: 찾으시는 결과가 없어요. 다른 검색어로 찾아볼까요?
```

## Before/After 종합 예시

```
케이스 1 — 일반 에러
원본: 오류가 발생하였습니다.
개선: 문제가 생겼어요. 잠시 후 다시 시도해볼게요.
이유: "오류" 제거, 주체 숨김, 해결 경로 제시.

케이스 2 — 입력 검증
원본: 올바르지 않은 형식입니다.
개선: 이메일 형식이 맞지 않아요. 예: name@domain.com
이유: 구체성(어떤 형식이 잘못됐는지) + 예시 제공.

케이스 3 — 권한 제한
원본: 접근 권한이 없습니다.
개선: 이 기능은 유료 회원만 사용할 수 있어요. [멤버십 알아보기]
이유: 제한 + 해결 경로. 업셀링 기회로 전환.

케이스 4 — 결제 실패
원본: 결제 실패
개선: 결제를 완료하지 못했어요. 카드 정보를 확인하고 다시 시도해볼게요.
이유: 능동형, "실패" 단어 제거, 구체적 해결 경로.

케이스 5 — 404
원본: 페이지를 찾을 수 없습니다.
개선: 찾으시는 페이지가 없어요. [홈으로 가기]
이유: 막다른 길 → 다음 행동 연결.

케이스 6 — 빈 목록
원본: 주문 내역이 없습니다.
개선: 아직 주문한 내역이 없어요. [쇼핑 시작하기]
이유: 빈 상태를 전환 기회로 활용.
```
