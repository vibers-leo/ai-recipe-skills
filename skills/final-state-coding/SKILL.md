# 최종상태코딩

사용자 표현을 보존하고 완성된 제품을 누가 어떤 상황에서 어떻게 쓰는지 먼저 그린다. 사용자가 빠뜨린 중요한 결과와 예외를 기대 효과·비용과 함께 제안하되 임의로 범위를 확장하지 않는다. 계획으로 끝내지 않고 현재 요청과 권한에 속하는 구현·검증을 진행한다. 기존 원장, 작업 이력, 로컬 변경과 프로젝트 지침을 먼저 읽고 완료된 작업을 반복하거나 덮어쓰지 않는다.

## 결과에서 역순으로

1. 최종 사용자·관리자·운영자별 목표, 시작 조건, 정상 흐름, 오류·복구·인수인계와 실제 사용 장면을 구체화한다. 적용되지 않는 역할은 이유를 남긴다. 사용자 원문, 확인된 사실, 미확인 가정과 AI의 제안을 분리한다.
2. 완료 기준을 관찰 가능한 행동과 검증 방법·환경·증거로 정의한다. 정량 목표는 지표·기준값·목표·측정기간을 명시하고 근거 없는 수치는 잠정 제안으로 표시한다. 확정하지 않은 가정을 충족 사실로 취급하지 않는다.
3. 기존 제품과 모듈의 실제 코드·버전·테스트·배포·운영 근거를 확인하고, 강점을 이식하거나 복제할 수 있는지 평가한다. 출처·라이선스·권리·호환성·유지보수·고객 데이터와 계정 분리·비밀값 제거를 확인한다. 구현 여부와 운영에서 검증된 여부를 분리한다. 불명확하면 후보로 남긴다. 기존 모듈의 사용 조건을 확인한다.
4. 실제 사용 환경과 유통·기기 기능을 근거로 웹·모바일 웹·앱 등 형식을 결정한다. 기존 팀 역량과 운영 비용, 보안·유지보수 및 재사용 가능성을 비교해 스택을 간소화한다. 실제 지원 범위·권한·계약·정산·테넌트 격리·마이그레이션을 확인하기 전 완료되었다고 가정하지 않는다.
5. 검수와 수정 여유를 포함해 목표일에서 역산한다: 완성본 검수 → 통합 검증 → 기능 구현 → 의존성·재사용 검증. 범위·가용량·의존성·외부 심사 근거가 부족하면 날짜는 잠정으로 표시하고 확약하지 않는다. 사용자 제공 마감과 개발 완료·검수·공개 일자를 구분한다.
6. 요청된 범위 안에서 구현하고 실제 사용자 흐름을 검증한다. 해당되는 통합·실패 및 복구·접근 권한·결제 성공/실패/중복/취소를 안전한 테스트 환경에서 확인한다. 실제 결제나 운영 데이터는 별도 권한에 따른다. 미실행·실패는 완료로 쓰지 않는다.
7. 합의된 범위의 필수 전체 흐름을 검수 전에 구현하고 자체 검증해 완성본으로 제시한다. 검수 가능한 완성본에는 실행/접속 방법, 역할별 시나리오, 완료 기준과 테스트 증거, 알려진 제한·미확인 사항, 운영·복구 및 인계 방법을 묶는다. 구현 완료, 테스트 통과, 운영 배포, 실사용 및 사용자 검수를 별도 상태로 기록한다. [작업 양식](references/template.md)을 필요한 만큼 사용한다.

## 매일 실행

기존 프로젝트 원장과 예약을 확인하고 중복을 만들지 않는다. 변경과 실패, 마감과 의존성을 확인해 근거 있는 작은 개선을 우선 구현·테스트하고 결과와 다음 행동을 기록한다. 일일 보고는 검수 가능한 완성물, 해결한 문제와 검증 근거, 사용자 결정 사항, 다음 완성 목표를 중심으로 한다. 작업하지 못한 범위와 이유를 명시하고, 관찰만으로 해결이나 정상 운영을 주장하지 않는다. 기존 사용자 변경과 다른 실행자를 보존한다. 새 자동화는 요청과 실행 환경, 시간대, 범위, 실패·비용·중복 제어를 확인한 후에만 설정하고 첫 실제 실행을 확인한다.

이 스킬 자체는 운영 배포, 삭제, 인증·권한 변경, 실결제·결제 설정 변경, 외부 발송을 허가하지 않는다. 해당 작업은 현재 요청과 적용되는 승인·권한을 확인하고 필요한 경우 구체적 결과와 영향·복구 방안을 준비한 뒤 승인받는다. 로컬 수정과 검증은 허용된 범위에서 계속한다.
